## Invocation

The exact commands run, verbatim and reproducible — no ellipses, no placeholders. `$REPO` is the
repository root.

```bash
mkdir -p /tmp/openrpc-verdict && cd /tmp/openrpc-verdict

# 1. the pinned validator, the pinned meta-schema sources, and the cross-check tool
npm install --no-audit --no-fund \
    ajv@8.17.1 ajv-cli@5.0.0 \
    @open-rpc/spec-types@0.0.2 @open-rpc/meta-schema@1.14.9 @open-rpc/schema-utils-js@2.2.1

# 2. the OpenRPC 1.4 meta-schema, extracted from the package that publishes it
node -e "require('fs').writeFileSync('openrpc-1.4-meta-schema.json', JSON.stringify(require('@open-rpc/spec-types').spec.OpenRPCSpecificationSchema1_4, null, 2))"

# 3. the JSON Schema meta-schema it $refs, plus a no-trailing-slash alias of it (note 2)
curl -sS -L https://meta.json-schema.tools/ -o meta-json-schema-tools.json
node -e "const s=require('./meta-json-schema-tools.json'); s['\$id']='https://meta.json-schema.tools'; require('fs').writeFileSync('meta-json-schema-tools-noslash.json', JSON.stringify(s, null, 2))"

# 4. the document under test
cp $REPO/extra/cloud-jsonrpc/src/test/resources/io/activej/jsonrpc/openrpc/reference-api.openrpc.json .

# 5. validate
./node_modules/.bin/ajv validate \
    -s openrpc-1.4-meta-schema.json \
    -m meta-json-schema-tools.json -m meta-json-schema-tools-noslash.json \
    -d reference-api.openrpc.json \
    --spec=draft7 --strict=false --all-errors --errors=text
```

## Notes

### 1. `https://meta.open-rpc.org/` currently serves a **1.3-era** meta-schema, and it rejects `1.4.0`

This is the one thing a later reader must not be surprised by. Running the same validation against
npm `@open-rpc/meta-schema@1.14.9` — whose body is byte-identical to what `https://meta.open-rpc.org/`
serves today (verified: `JSON.stringify(pkg, null, 2)` of the package export has the same sha256,
`6b62c3ca1c8230c79058a4ff25e6bd9abbad0a43bd86b52853af2b551fbeeea8`, as the fetched document) —
produces exactly one error:

```bash
node -e "require('fs').writeFileSync('openrpc-1.3-meta-schema.json', JSON.stringify(require('@open-rpc/meta-schema').default, null, 2))"
./node_modules/.bin/ajv validate \
    -s openrpc-1.3-meta-schema.json \
    -m meta-json-schema-tools.json -m meta-json-schema-tools-noslash.json \
    -d reference-api.openrpc.json \
    --spec=draft7 --strict=false --all-errors --errors=text
```

```text
reference-api.openrpc.json invalid
data/openrpc must be equal to one of the allowed values
```

Its `properties.openrpc` is an **enum** whose newest member is `1.3.2`. That package was last
published **2024-05-08**; OpenRPC `v1.4.0` and `v1.4.1` were released **2026-02-24** and
**2026-02-25**, and `open-rpc/meta-schema`'s `master/schema.json` carries a build-time placeholder
where that enum goes ("GENERATED FIELD: Do Not Edit"), so no 1.4-aware release of *that* package
exists. The 1.4 meta-schema is published in `@open-rpc/spec-types` instead, which is what this
verdict validated against and what the project's own validator selects for a `1.4.x` document.

**Control run** — the same document with `openrpc` replaced by `1.3.2` and nothing else changed,
against the 1.3-era meta-schema:

```bash
node -e "const d=require('./reference-api.openrpc.json'); d.openrpc='1.3.2'; require('fs').writeFileSync('control-openrpc-1.3.2.json', JSON.stringify(d))"
./node_modules/.bin/ajv validate \
    -s openrpc-1.3-meta-schema.json \
    -m meta-json-schema-tools.json -m meta-json-schema-tools-noslash.json \
    -d control-openrpc-1.3.2.json \
    --spec=draft7 --strict=false --all-errors --errors=text
```

```text
control-openrpc-1.3.2.json valid
```

So the enum is the *only* thing the older meta-schema objects to: every method, Content Descriptor,
`paramStructure`, absent-`result` notification marker and `schema` fragment — including the boolean
`true` fallbacks — satisfies both meta-schemas.

### 2. Two registrations of `https://meta.json-schema.tools` are needed, one of them an alias

The OpenRPC meta-schema's `definitions.JSONSchema` is `{"$ref": "https://meta.json-schema.tools"}`
(**no** trailing slash), while the document served at that URL declares
`"$id": "https://meta.json-schema.tools/"` (**with** one). ajv's lookup is exact, so registering
only the fetched file fails with `can't resolve reference https://meta.json-schema.tools from id
https://meta.open-rpc.org/` and the `schema` members go unchecked. Step 3 above therefore registers
the fetched document twice: once as published, once as a copy whose `$id` has the slash removed.
Nothing else in either copy is altered.

That reference is load-bearing rather than cosmetic — see the negative controls below, where a
malformed `schema` member is caught at `data/methods/0/params/0/schema/type`, which is only
reachable through it.

### 3. The pass is not vacuous — negative controls

A validator wired wrong reports "valid" for everything, so four deliberately broken copies of the
frozen document were run through the identical invocation (step 5, with `-d <copy>.json`). Every one
was rejected — first reported error quoted, `--all-errors` produces more:

```bash
node -e "
const fs=require('fs');
const base=()=>JSON.parse(fs.readFileSync('reference-api.openrpc.json','utf8'));
let d=base(); delete d.info;                              fs.writeFileSync('neg-no-info.json', JSON.stringify(d));
d=base(); delete d.methods[0].name;                       fs.writeFileSync('neg-nameless-method.json', JSON.stringify(d));
d=base(); d.methods[9].paramStructure='sideways';         fs.writeFileSync('neg-bad-paramstructure.json', JSON.stringify(d));
d=base(); d.methods[0].params[0].schema={type:'not-a-type'}; fs.writeFileSync('neg-bad-schema.json', JSON.stringify(d));
"
```


| Mutation | Reported |
|---|---|
| `info` removed | `data must have required property 'info'` |
| a method's `name` removed | `data/methods/0 must have required property 'name'` |
| `paramStructure` set to `"sideways"` | `data/methods/9/paramStructure must be equal to one of the allowed values` |
| a param's `schema` set to `{"type":"not-a-type"}` | `data/methods/0/params/0/schema/type must be equal to one of the allowed values` |

### 4. Network use

The npm install and the one `curl` of `https://meta.json-schema.tools/` happen **here**, in a
developer's sandbox, at validation time. Nothing in the repository, the Maven build or
`OpenRpcSchemaTest` fetches anything: the test reads one classpath resource and compares two byte
arrays (FR-051, SC-003).

⚠ A recorded verdict is only ever **pass**. A failing run is fixed — in the mapping or in the
fixture — regenerated per `README.md`, and validated again *before* the reference is committed; it
is not recorded here and shipped as a known-bad reference. Note 1 is not an exception to that rule:
the document **passes** the meta-schema for the OpenRPC version it declares. It is recorded because
a later reader validating against `https://meta.open-rpc.org/` will see one error and needs to know
it is the published meta-schema lagging the specification, not this document drifting.
